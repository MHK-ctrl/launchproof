# LaunchProof v0.1.0 — Source Preview Release Notes

**Release date:** 2026-11-23
**Status:** Public source preview. Not published to npm. The website and optional cloud dashboard are
not deployed.
**License:** MIT

> **Later update:** after this draft, an optional cloud dashboard, Supabase RLS schema, GitHub
> sign-in/repository connection, and explicit CLI upload were implemented. They remain undeployed and
> untested against live Supabase/GitHub credentials. The local-first statements below still describe
> the default core workflow; see [CLOUD_DASHBOARD_ARCHITECTURE.md](CLOUD_DASHBOARD_ARCHITECTURE.md)
> for the cloud scope.

LaunchProof is a local-first verification CLI for applications built with AI coding tools. It checks
security posture, secrets, API contracts, object-level authorization, browser workflows,
accessibility, and performance, then writes evidence you can inspect instead of a badge you have to
trust.

This is the first public source preview. It is intended for developers who want honest, bounded
verification on their own machine, and for reviewers who want to see how the result was produced.

## Highlights

- **Evidence over badges.** Every check reports `pass`, `fail`, `warn`, `skipped`, `not-verified`, or
  `error`, with findings, evidence, impact, and remediation.
- **Local-first.** No account, telemetry, hosted dashboard, or Docker required. The default scan is
  static and offline.
- **Authorization-aware.** Remote targets require explicit authorization and host scope; private
  networks require a separate opt-in; metadata hosts are blocked.
- **Bounded.** File walk, HTTP budget, response size, browser pages, links, concurrency, and timeouts
  are capped for laptop use.
- **Self-contained reports.** Terminal, offline HTML, JSON, and SARIF 2.1.0 are generated from one
  report object.
- **Honest coverage.** Missing browser dependencies, unavailable Lighthouse, unverified Supabase
  state, and skipped checks are never reported as passes.

## What is included

### CLI

Commands: `init`, `analyze`, `test`, `security`, `scan`, `browser`, `accessibility`, `performance`,
`report`, `config`, and `doctor`.

Global modes and flags include `--config`, `--json`, `--quiet`, `--verbose`, `--ci`, `--no-color`,
`--output`, and `--fail-on`. Exit codes are `0` (gate passed), `1` (gate failed), `2` (usage,
configuration, or authorization error), and `3` (unexpected error).

### Verification

- Bounded project discovery: frameworks, languages, package manager, scripts, API routes, environment
  references, deployment targets, integrations, and test tools.
- Secret scanning with provider patterns, entropy heuristics, placeholder filtering, `.env` hygiene,
  tracked-file checks, and optional bounded git-history filename checks.
- Static rules for dynamic code execution, raw HTML sinks, shell/SQL interpolation, permissive CORS,
  disabled TLS verification, service-role usage, environment logging, and unsafe build flags.
- Repository hygiene: `.gitignore`, lockfile, CI, README, license, and unsafe build flags.
- Optional npm audit with network checks enabled.
- Bounded HTTP checks: security headers, cookies, CORS, transport, sensitive paths, error leakage, and
  reachability, with per-hop redirect scope validation.
- API contracts for configured endpoints and OpenAPI-derived paths, identity resolution, JSON shape,
  status, latency, and anonymous access.
- Read-only two-identity object-level authorization probes with inconclusive handling for unexpected
  responses.
- Supabase static RLS review and an optional read-only anon-key live probe.
- Playwright browser checks: page load, console and failed-request capture, configured workflows,
  internal links, mobile overflow, screenshots, axe-core accessibility, and navigation performance
  budgets.
- Terminal, self-contained HTML, JSON, and SARIF 2.1.0 reports with redaction, limitations, and a
  gate.

### Website

A static Next.js website with a landing page, clearly labeled simulated demo, real sample-report
viewer, documentation, get-started, about, security, and not-found routes. It has no analytics,
account system, fake metrics, testimonials, or customer logos.

### Demos

- `examples/vulnerable-demo` — intentionally insecure loopback target. Its scan fails the configured
  gate as expected.
- `examples/secure-demo` — hardened contrast target with strict headers, authenticated APIs,
  ownership checks, and a strict CSP. Its scan passes the checks it supports.

## Installation

LaunchProof is **not published to npm** in this release. Install from source:

```bash
git clone https://github.com/MHK-ctrl/launchproof.git
cd LaunchProof
npm install
npm run build
node packages/cli/bin/launchproof.mjs --help
```

Requirements:

- Node.js **22.12+** (tested locally on Node 26 / macOS arm64; CI covers Node 22 and 24).
- npm with the committed lockfile.
- No Docker, database, or hosted service.

Optional browser runtime:

```bash
npm install --save-dev playwright axe-core
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npx playwright install --only-shell chromium
```

Then enable `browser.enabled` and set `app.url` in `launchproof.config.json`.

## Quick start

```bash
node packages/cli/bin/launchproof.mjs init
node packages/cli/bin/launchproof.mjs analyze
node packages/cli/bin/launchproof.mjs test
```

The generated configuration is conservative: network checks are off by default. Browser checks run
only when enabled and when the optional runtime is installed.

To try the demos:

```bash
npm run demo:vulnerable   # http://127.0.0.1:4173
npm run demo:secure       # http://127.0.0.1:4174
```

From `examples/vulnerable-demo`, with the demo running:

```bash
LP_DEMO_OWNER_ID=1 LP_DEMO_OTHER_ID=2 \
  node ../../packages/cli/bin/launchproof.mjs test
```

The vulnerable demo is expected to fail its gate. The sample report on the website is its real output,
not a benchmark or a customer scan.

## Security notes

- Remote testing requires explicit authorization and a matching host scope.
- Loopback is allowed by default; private networks require an additional opt-in.
- Cloud metadata hosts are blocked.
- URL-embedded credentials are rejected.
- Redirects are re-checked per hop; cross-origin redirects do not retain caller headers or bodies.
- Browser checks block cross-origin navigation and strip identity headers from cross-origin
  subresources.
- Unsafe API methods and authorization mutations are disabled by default.
- Secret-like values are masked before findings are created; response bodies are excluded from
  evidence.
- HTML reports are escaped, offline, and free of remote scripts.
- The report reader validates structure, vocabularies, control characters, and a 25 MB cap.
- Optional AI remediation is consent-gated and sends no evidence values.
- No telemetry is collected.

## Known limitations

- No independent security audit or penetration test has been performed.
- Static rules and secret detection are heuristics, not exploit proof.
- TLS certificate chains, protocol versions, cipher suites, and revocation are not assessed.
- Scope checks are host-pattern based and do not resolve DNS; DNS rebinding is not defended against.
  Do not scan untrusted targets from a sensitive host.
- HTTP checks are unauthenticated unless identities are configured.
- Authorization probes cover configured scenarios only and are read-only by default.
- Supabase static analysis cannot prove deployed policy state; no real Supabase project was tested.
- Browser checks cover configured workflows and sampled pages in headless Chromium only; Safari,
  Firefox, and real mobile devices are not covered.
- axe-core covers a subset of WCAG; manual accessibility testing remains necessary.
- Performance numbers are single local observations, not production benchmarks.
- Lighthouse is not bundled; requesting it yields `not-verified`.
- Git-history scanning is filename-based and bounded.
- Windows and Linux desktop behavior are not manually validated; CI covers Linux.
- The website has no canonical URL or sitemap until a real deployment host exists.
- The source repository is public; no website deployment or npm package exists at the time of
  writing.

## Compatibility and upgrade notes

- This is the first release; there is no migration path from an earlier version.
- The report schema version is `1`.
- Node.js 22.12+ is required.
- Playwright and axe-core are optional peers; missing dependencies produce `not-verified`, not a pass.
